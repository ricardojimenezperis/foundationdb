# by5eval: resolver v1 against FDB's skip list at 6 GiB

These scripts reproduce the comparison of btree-v1 (resolver v1) with FoundationDB's skip list
when both keep at most 6 GiB of conflict history: how much history each retains, and how long
each takes to resolve the same batches.

## Revisions

| Role | Revision |
|---|---|
| Resolver v1 source (`fdbserver/resolver/resolver1`) | `aff127286e68ea7933dc9ef502a7dbd760e1e43d` |
| FoundationDB base | `746d04926c6b30b7fb5ba3b4dfa3bfca19f56e9c` (upstream `main`) |
| Harness, statistics and unit tests; FDB baseline binary | `1dfa7ffe6a5210c66e36a628552d10a7046649d0` |
| Batch replayer (smoke test) | `99dfd66085dc7319b28033f67ff71067694125d0` |
| FoundationDB integration of btree-v1 | `c44fd2247be51c26ca48c56dcc0587fb7b54ea04` |

The FDB baseline is built from the harness commit, where `ConflictSet` still keeps FDB's skip
list. btree-v1 is built from the integration commit or any later commit of this branch.

### Relation to the evaluated binaries

The evaluation ran binaries built from a private repository, where the btree-v1 integration
(commit `5a07ab1936`) sat on a base with other conflict histories, which are not part of this
publication. On this branch, the harness and the integration are taken from those commits
without them:

- **Selection of btree-v1.** In the evaluated binary, btree-v1 resolved every batch, whatever
  the knobs selected. That base also had a knob that chose among its other histories, and the
  runs set `--knob_resolver_use_paged_conflict_set=0`, which chooses FDB's skip list, so that
  none of them was built beside btree-v1. `--knob_paged_resolver_pool_pages=98300` gave btree-v1
  its pool: 98,300 pages of 64 KiB, 6,442,188,800 bytes. On this branch btree-v1 is the only
  history and `PAGED_RESOLVER_POOL_PAGES` its only knob; the first option does not exist.
- **FDB's arm.** It ran a binary of that base with the same knob set to FDB's skip list, with a
  window of 265 s. Here it is the harness commit's binary.
- **Build patches.** The evaluated measurement binaries were built with patches over the
  evaluated sources: one that keeps the logs in memory (timing builds), one that counts the
  history's bytes (accounting builds) and, for btree-v1, one that made the harness treat it as a
  history kept by capacity. The published harness does the last itself, for any history whose
  statistics say so (`ConflictSetStats::paged`); `by5-membuf.py` is the first, unchanged;
  `by5-acct.py` is the second, for the histories of this branch.

The validation in `EVIDENCE.md` shows that the published binaries decide and log as the
evaluated ones.

## Workload

- Trace: `pilot-2000M-l0-7200.trace`, 7,200 s of model time, generated by `../by5gen` with
  `--domain 2000000000 --long-ppm 0 --warmup 6900 --measure 300`, seed 1: 65,536 transactions per
  second in batches of 2,048 (32 batches per second), one read and one write each, reads
  1.5625 s old, 7,300 conflicts per million. 15,099,494,528 bytes, SHA-256
  `0c0d343969fe2e91ef95c09b765b74d078bc9ed48ccf2df15d9dd9db3fd4b6c2`.
- Segment: batches [57,600, 230,400) of the trace, 172,800 batches (5,400 s), from a cold history
  (`BY5_SEGMENT_START=57600`, `BY5_PREHISTORY_BATCHES=57600`, `BY5_PRIME=0`).
- Budget: 6 GiB of history, 6,442,450,944 bytes.
  - FDB's skip list keeps history by a window. 265 s is the largest window whose live history,
    counted by the accounting build, stays within the budget on this trace, as calibrated before
    the campaign. In the campaign its accounting run peaked at 6,354,541,376 bytes, 98.64% of the
    budget. `budget-watch.sh` stops an accounting run of FDB as soon as its history exceeds the
    budget, so a window that does not fit is discarded.
  - btree-v1 keeps history by capacity, in a pool of 98,300 pages: 6,442,188,800 bytes, its whole
    history.

## Build

1. Configure and build both revisions with the FoundationDB toolchain (the evaluation used the
   `foundationdb/build:rockylinux9-latest` image, digest
   `sha256:591bb3f7b9a8c83ca8ddac97f0d05239532d0dd03eef411094e9fc23766879f7`, with Clang and
   libc++):

   ```sh
   git worktree add --detach wt-fdb 1dfa7ffe6a5210c66e36a628552d10a7046649d0
   git worktree add --detach wt-v1 resolver-v1
   for n in fdb v1; do
     mkdir build-$n && cd build-$n
     cmake -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=clang \
           -DCMAKE_CXX_COMPILER=clang++ -DUSE_LIBCXX=1 -DUSE_LD=LLD ../wt-$n
     ninja fdbserver && cd ..
   done
   ```

2. Build the measurement binaries, with the same toolchain and paths:

   ```sh
   for n in fdb v1; do for k in nativemem acct; do
     fdbserver/resolver/by5eval/build.sh wt-$n build-$n $k bin/$n-$k
   done; done
   ```

   `nativemem` keeps the per-batch logs in memory until the run ends; `acct` counts the
   history's bytes every batch. Both keep the tree's compiler and flags.

## Runs

- One run: `TRACE=... run.sh ARM BIN OUT CPU`, with `ARM` = `fdb265` or `v1`.
  - `fdb265` sets `BY5_WINDOW_US=265000000`; `v1` passes
    `--knob_paged_resolver_pool_pages=98300` and no window.
  - The process pins itself to `CPU` (`BY5_CPU`) and `run.sh` starts it under `taskset`.
- The campaign: `TRACE=... campaign.sh OUT bin/fdb bin/v1` (with `bin/fdb/{nativemem,acct}` and
  `bin/v1/{nativemem,acct}`).
  1. **Accounting runs** (`acct`), one per arm, at once on `ACCT_CPUS`. They are not timed. They give
     retention (`retained_us` in `batches.csv`) and memory (`history_bytes` in
     `batches.csv.acct.csv`).
  2. **Native timing runs** (`nativemem`): three rounds, one run at a time on `TIMED_CPU`, with
     the order of the arms alternated: fdb265, v1; v1, fdb265; v1, fdb265.
  - Between runs the page cache is drained; `vm.nr_hugepages` is 3,300 during the campaign.
- Measurement conditions of the evaluation (Hetzner, AMD Ryzen 7 7700, Linux 6.8): each run in
  `docker run --cpuset-cpus=CPU --cpuset-mems=0` with the toolchain image; timed runs on
  physical core 7 (CPU 7), its SMT sibling (CPU 15) idle, no other process, build or analysis
  on the machine; accounting runs on CPUs 1 to 4.

## Analysis

`analyze.py OUT` reports, from the campaign's directories:

- the hashes of what every run was offered and decided, which must all agree;
- for each arm, the first batch in which retained history falls below the time elapsed, and the
  retention after it, by blocks of 600 s and over the steady state (batches 76,800 to 172,800,
  2,400 to 5,400 s);
- the peak of `history_bytes` against the budget;
- native times over the initial cut, the steady state and the whole segment, with medians and
  ranges of the three rounds, and v1/fdb265 paired by round.

By default the initial cut ends at the first discard of either arm. The evaluated campaign also
ran other arms, and its initial cut ended at batch 12,900; `analyze.py OUT 12900` reproduces it.
